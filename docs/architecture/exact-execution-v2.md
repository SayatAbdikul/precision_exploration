# Prepared exact execution extension

This opt-in engine lives in `tools/exact_execution_v2/`. Historical numerical
sources, native libraries, graph identities, A/B campaigns and acceptance
certificates remain unchanged. The extension runs the existing exact CPU/CUDA
MAC implementations; it does not dequantize candidate computation to FP32.

## What changes

- `PreparedGraph` validates and hashes an owned graph snapshot once, builds
  immutable constant tensors once, and checks each invocation's inputs.
- `PreparedOperators` retains native preparation of immutable weights within
  that graph instance. Runtime inputs are still prepared independently.
- Integer residual alignment and addition use tables generated by the original
  exact scalar oracles. Signed sums are indexed with safe host integer widths;
  accumulator rounding and final quantization are still evaluated by the
  declared oracle. Unsupported domains use the unchanged reference operator.
- The existing exact integer output-store extension is reused, with its
  existing fail-closed domain checks and reference fallback.
- If only some channels exceed that store's existing scale bounds, the scalar
  fallback is applied to those channels. Original NCHW ordering and a single
  combined pre-store diagnostic observation are preserved. No scale bound is
  relaxed, and no new numerical approximation is admitted.
- Layer output hashes and diagnostics remain part of validation. The frozen
  activation oracle reports some diagnostic stores only on cache misses; the
  validation harness records/replays its ordered cache history when resuming.
- Tensor hashes use byte-identical canonical JSON serialization of already
  validated tensors, avoiding redundant deep copies and recursive code walks.

Caching does not permit a changed reduction order. A cached graph owns its
snapshot; modifying the caller's source document requires constructing a new
instance. Each worker owns its engine and caches. Global activation tracing is
confined to an isolated validation process, not a thread-safe shared engine.

The mixed-channel store is an exact decomposition of the original store: for
an output index `(batch, channel, spatial)`, bias, scale, activation and final
quantization depend only on that index's accumulator value and that channel's
parameters. There is no reduction across channels in this operation. Executing
each channel independently and restoring the original flattened order therefore
preserves every output code. The joined lazy pre-store sequence restores that
same order for the unchanged diagnostic observer, which is called once for the
whole tensor. Unit tests cover batch/channel addressing, extreme accumulator
codes, saturating bias, unsupported scales and every observed pre-store value.

## Validation and resume

From the repository root:

```bash
.venv/bin/python -m tools.run.exact_execution
```

The default validates ResNet18 and MobileNetV2 INT4/5/6/8, with eight frozen
pilot images per graph, four worker processes and four CPU threads per worker.
It compares all layer codes/hashes, final outputs, execution strategies and
quantizer-event signatures to the retained accepted pilots. It acquires the
existing controller and native resource locks, and fails if another native
campaign owns them. The process needs access to the workstation's CUDA device.
Workers inherit and check all three kernel leases, keeping them held even if
the parent exits while a worker is finishing an image.

The command resumes sealed image checkpoints under a content-addressed job
identity and skips verified complete jobs. Source/dependency changes create new
validation identities. Partial resume reconstructs the activation cache history
without rerunning completed image inference. Incomplete evidence cannot grant
an eight-image compatibility status.

For a single-worker comparison with the previous exact integer-store path:

```bash
.venv/bin/python -m tools.run.exact_execution --models resnet18 --formats int4 --workers 1 --images 8 --baseline-images 2
```

Timing includes layer diagnostics and host execution, but not graph setup in the
per-image number. Setup and invocation wall time are reported separately. The
prepared and legacy passes both begin with cold activation caches; the prepared
pass runs first. Concurrent-suite latency includes contention and must not be
quoted as isolated latency or native hardware throughput.

## Evidence and scope

Evidence is written under `artifacts/exact_execution_v2/`, with sealed plans,
per-image records, per-graph validation reports and suite reports. These are
compatibility/performance diagnostics, not new quality screens, historical
acceptance amendments, or completion of D4. Certification applies only to the
graphs, images, dependency hashes and extension identities actually checked.
Implementation source files and each suite invocation are preserved separately;
a no-op resume does not overwrite earlier performance measurements.
Noninteger and detector acceptance remains governed by the frozen comparison
matrix and existing numerical gates.

Tests in `tests/unit/test_exact_execution_v2.py` cover exhaustive integer
residual input pairs, exact diagnostic values, scale extremes, reference
fallback, immutable graph ownership, input/manifest rejection and activation
cache replay. The original integer-store boundary tests are also required.

The saved-prediction analysis and next experimental design are documented in
`docs/analysis/saved-prediction-study-v1.md`; its versioned, sealed comparison
matrix preserves every datatype/model pair and labels unavailable arms.
