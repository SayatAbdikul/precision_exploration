Research & chip-development plan

Exploration of Precision and Data Types for a Sub-8-Bit Edge AI Inference Accelerator

A structured plan to identify the best numerical representation for the MANT edge-AI chip while producing a rigorous, publishable study of accuracy–area–energy–performance trade-offs across modern CNN workloads.

Target: ≤8-bit inference Workloads: edge CNNs Evaluation: accuracy + RTL/PPA Chip: MANT spatial fabric Goal: Pareto-optimal numerical architecture

1. Executive assessment

Conclusion: the exploration can be designed so that the same engineering effort both selects the numerical format for the chip and forms the basis of an independent research paper. The key is to study the complete numerical architecture—not just multiplier area.

The project is most valuable if it asks a broader question than “which 6-bit or 8-bit format gives the best accuracy?” The stronger question is:

Which sub-8-bit numerical representation gives the best accuracy–area–energy–throughput trade-off for real edge CNN inference under actual silicon constraints?

This matters particularly for MANT because its numerical format influences not only arithmetic, but also memory width, accumulator width, interconnect width, tile cost, tile count, communication energy, and whole-chip throughput.

Important architectural point: the current MANT specification assumes floating-point-only arithmetic. For a scientifically strong exploration, that should be treated as a design hypothesis during research rather than as an untouchable assumption. Otherwise the study can only answer “which floating-point format is best?”

2. Research questions

Q1 — Numerical quality Which representation preserves inference accuracy best at 4–8 bits?
Q2 — Arithmetic cost What is the real hardware cost of each representation when decode, multiply, accumulation, rounding and scaling are included?
Q3 — Chip-level efficiency At equal silicon area and accuracy, which representation produces the best MANT chip?

Core hypothesis

The format with the smallest multiplier will not necessarily produce the smallest or most energy-efficient accelerator. At ultra-low precision, memory, scaling logic, accumulator width and communication can dominate total hardware cost.

Potential higher-level finding

There may be no globally optimal numerical format. The best format may depend on network, layer type, tensor distribution, accuracy target, accumulator precision and hardware budget. This can naturally lead to mixed-precision or heterogeneous-tile designs.

4. Candidate data-type universe

The exact experimental datatype set is not frozen yet. At this stage, the plan defines a broad candidate universe and groups it into families. A smaller final set will be selected after a pilot study based on relevance, implementability, overlap between formats, and expected hardware value.

The study targets 8-bit and smaller representations for weights and activations. “All possible datatypes” is not literally finite because arbitrary custom encodings can always be invented, so the goal is to cover all major practically relevant numerical families used or proposed for low-precision neural-network inference.

5. Quantization methodology

Quantization method and number representation must be separated experimentally. Otherwise a strong quantizer can make a weak representation appear superior. This project uses post-training quantization only: all candidates start from the same pretrained floating-point checkpoints, and the exploration does not include model retraining.

Scale search

  1. evaluate approximately 100 coarse clipping/scale candidates,
  2. identify the lowest-MSE region,
  3. evaluate approximately 50 finer candidates around that region,
  4. store the lowest-MSE scale for that tensor and datatype.

Exact quality evaluation after PTQ

The research paper should not depend on the private MANT architecture or its golden model. Accuracy should therefore be measured using an architecture-independent bit-exact numerical inference engine. Quantized tensors are stored as actual low-precision codes, and arithmetic follows the published semantics of each datatype.

pi = RoundF(xi × wi),    ai = RoundA(ai−1 + pi)

This is distinct from ordinary fake quantization, where tensors may be constrained to quantized values while convolution/GEMM still uses unrestricted FP32 accumulation. High-precision arithmetic may be used internally only as an oracle for generating the correctly rounded low-precision result.

This should be a first-class experiment, not a detail. The current MANT semantics round each multiplication and each accumulation in the active format, which can cause large error at 4–6 bits.

7. Hardware evaluation must be hierarchical

A standalone multiplier comparison is useful, but insufficient. The same format can look cheap at multiplier level and expensive at tile level, or vice versa.

LevelIncludesWhy it matters
1. Arithmetic primitive multiplier, adder, optional decode/normalize blocks explains fundamental arithmetic cost
2. Complete MAC / FPU decode, multiply, accumulate, normalize, round, scale handling, saturation fair format-to-format compute comparison
3. Complete MANT tile FPU + A/B + memory + control + bus + format logic determines the actual replicated unit cost
4. Whole chip tile count, workload mapping, communication, clock and area budget identifies the real chip winner

Multiplier architecture exploration

For integer and mantissa multiplication, synthesize several candidate structures and keep the Pareto-optimal implementation:

  • array multiplier,
  • shift/add,
  • radix-4 Booth,
  • Booth + Wallace,
  • Booth + Dadda.

At tiny widths, additional encoding/reduction logic can outweigh the expected savings. Do not assume the textbook “best” multiplier is best at 4–8 bits.

9. MANT-specific experiments

9.1 Signed vs unsigned activations

Because many post-ReLU tensors are non-negative, MANT can potentially reuse the sign bit as extra mantissa or exponent capacity. Compare signed and unsigned versions of equal total width.

9.2 Same-format vs wider accumulation

This is likely one of the most important MANT decisions because widening the whole word also widens private memory and communication. A narrow-storage / wide-accumulator architecture may be a strong design point.

9.3 Uniform precision first

The first chip should probably use one dominant format. This simplifies RTL, verification and physical design. Mixed precision should come after the best uniform format has been established.

9.4 Heterogeneous tile classes

If mixed-format inference becomes attractive, physical specialization is likely better than making every tile support every format. 

Example chip composition:
  FP8 tiles
  FP6 tiles
  FP4 / MXFP4 tiles
  optional higher-precision accumulation tiles

9.5 Conversion problem

Raw MANT memory words are untyped bit patterns. If different tiles use different representations, data exchange needs explicit conversion. Possible future solutions include:

  • conversion on sender before the write bus,
  • conversion at the destination memory interface,
  • a dedicated conversion instruction or conversion tile.

9.6 Activation-function compatibility

ResNet and MobileNetV2 are relatively straightforward. MobileNetV3 hard-swish can be decomposed into simple arithmetic and clipping. YOLO / EfficientNet variants using SiLU or Swish require a hardware-accurate approximation strategy, which must be included in end-to-end accuracy measurements.

10. Pareto analysis and chip-selection rule

Every numerical configuration should be represented as a point in a multi-objective space:

F → (ΔAccuracy, Area, Energy, Latency)

The main paper should show Pareto frontiers rather than only one weighted score. The final chip choice can then be made under explicit constraints.

Example selection rule

Require:

  • ImageNet Top-1 loss ≤ 1%,
  • COCO mAP loss ≤ 1 point,
  • latency within the target edge budget.

Then minimize energy per inference or maximize throughput/mm².

Iso-area comparison

A smaller tile means more tiles on the same die. Therefore the decisive comparison should include equal-silicon-budget experiments, not just “one FP6 tile vs one FP8 tile.”

Precise multiplication and accumulation model

Every experiment must separately specify operand format, product precision, accumulator datatype, rounding points, overflow/underflow behavior, accumulation order and requantization point.

Three MAC models

A. Native arithmetic

pi=RoundF(xiwi)
ai=RoundF(ai−1+pi)

Cheapest path: product and accumulator both use the operand datatype.

B. Rounded product + wider accumulator

pi=RoundF(xiwi)
ai=RoundA(ai−1+ConvertA(pi))

Multiplier output remains narrow while accumulation uses a wider format.

C. Full-product / FMA-style accumulation

ai=RoundA(ai−1+Exact(xiwi))

The product is not rounded back to operand precision before accumulation. This is the preferred clean numerical baseline.

Primary methodology: use Model C for controlled datatype comparison, then compare A/B/C for finalists to expose hardware–accuracy trade-offs.

BatchNorm folding and bias representation

Deployment graph must be frozen before PTQ

PTQ should operate on the graph that would actually be deployed, not on the unfused training graph. The preprocessing order is:

FP32 checkpoint → eval mode → fold BatchNorm → freeze deployment graph → collect calibration statistics → PTQ

BatchNorm is folded into the preceding convolution before quantization. For:

y = Wx + b
BN(y) = γ(y−μ)/√(σ²+ε) + β

define:

α = γ/√(σ²+ε)
W' = αW
b' = α(b−μ)+β

Quantization is applied to W' and the folded bias b'. Folding after weight quantization is not allowed because BatchNorm changes the deployed weight distribution and would invalidate the calibrated scale.

Frozen baseline: BatchNorm is always folded before calibration and PTQ.

Bias precision

Bias should not normally be forced into the 4–8-bit operand datatype because there is only one bias value per output channel. Its storage cost is small compared with model weights, while aggressive bias quantization can introduce avoidable error.

Integer-bias scale

For integer quantization:

x = sxqx,   w = swqw

therefore:

xw = (sxsw)(qxqw)

Bias must be represented in the same product/accumulator domain:

qb ≈ b/(sxsw)

With per-output-channel weight scales s_w[c], the effective bias scale is channel-specific:

sb[c] = sxsw[c]

Bias-addition point

The baseline adds bias once after the dot-product reduction and before activation/requantization:

a = Σ xiwi
y = RoundA(a + b)
output = QFout(activation(y))

This avoids repeatedly exposing the bias to accumulation rounding and provides a simple, deterministic numerical definition.

Exact inference-engine implementation

Purpose

The engine is an architecture-independent numerical evaluator. It must reproduce the specified datatype and accumulation semantics exactly without exposing or depending on MANT's private architecture.

Software stack

PyTorch model/data frontend → quantized graph → custom operator runtime → C++ / CUDA datatype backend

Use PyTorch for:

  • loading pretrained checkpoints,
  • datasets and preprocessing,
  • model-graph inspection and conversion,
  • calibration orchestration,
  • accuracy / mAP metric computation.

Replace numerically important quantized operators with custom exact kernels such as: QuantConv2d, QuantDepthwiseConv, QuantLinear, QuantAdd, and custom nonlinear LUT operators.

Why use uint8 storage initially?

Candidate datatypes are ≤8 bits, but CPUs and GPUs do not provide convenient addressable native types such as uint5, uint6 or uint7. Therefore the first implementation stores each encoded value in an 8-bit container: 

FP6 E3M2 stored in uint8:
bit 7 6 5 4 3 2 1 0
    0 0 S E E E M M
Important: uint8 is only a host-side simulation container. It does not mean FP6 is counted as 8 bits in the hardware analysis. Hardware storage, SRAM/bandwidth cost and RTL all use the actual datatype width.

Storage representation versus compute representation

Storage and arithmetic representation are intentionally separate. An encoded FP6 value may be stored as uint8, decoded to a wider exact temporary representation for computation, then explicitly rounded back according to the chosen FP6/accumulator semantics.

A fast backend may therefore use:

encoded low-precision code → exact decoded temporary → defined arithmetic → explicit low-precision rounding

This remains valid as long as the result is bit-for-bit identical to the exact datatype oracle.

Optional predecoded fast mode

Weights are heavily reused, so repeated decode cost may be avoided by predecoding weights into a wider compute representation. This is allowed for simulation speed because host memory usage is not the hardware-cost metric.

Maintain two modes:

  • encoded reference mode for correctness validation,
  • predecoded fast mode for large experiment sweeps.

Both modes must produce identical outputs.

Convolution implementation path

Start with im2col + custom GEMM for normal convolution because it minimizes implementation effort and concentrates optimization in one kernel. After numerical correctness is established, direct tiled convolution can replace im2col if memory traffic becomes a bottleneck.

Conv2D → im2col → exact custom GEMM

Dedicated depthwise convolution

MobileNet/EfficientNet rely heavily on depthwise convolution. Mapping depthwise convolution to generic GEMM can be inefficient, so implement a dedicated exact depthwise kernel early.

Initial kernel priority: custom GEMM + dedicated depthwise Conv. These cover most computation in ResNet, MobileNetV2/V3 and EfficientNet-style models.

Tensor layout

Begin with NCHW for compatibility with PyTorch and to avoid extra transposes. Consider NHWC only if profiling shows that channel-oriented vectorization or depthwise access patterns justify the conversion cost.

Deterministic reduction order

For the primary exact experiment, one logical accumulator owns each output element and processes the reduction dimension in deterministic order:

for k = 0…K−1:   acc = AddA(acc, Product(x[k],w[k]))

Parallelize across independent outputs rather than changing the accumulation tree. Tree reduction is a separate later ablation because low-precision rounded addition is not associative.

CPU backend

Implement a C++17/20 backend using multithreading (OpenMP, TBB, or a worker pool) and SIMD where practical. Parallelize over independent batch/output-channel/spatial outputs.

CUDA optimization strategy

The objective is not to reproduce cuDNN/TensorRT performance. The objective is to make thousands of exact-format experiments practical while preserving deterministic numerical semantics.

Stage 0 — benchmark before building the full runtime

Implement one representative standard convolution and one MobileNet depthwise convolution using FP6 E3M2. Compare three arithmetic backends:

  1. algorithmic decode/arithmetic/rounding,
  2. LUT-based arithmetic,
  3. predecoded values + explicit accumulator rounding.

Measure:

  • kernel latency,
  • effective MAC/s,
  • memory bandwidth,
  • GPU occupancy where available,
  • bit-for-bit output agreement.
Do not decide globally between LUT and algorithmic arithmetic until this benchmark is complete. The best method may differ by datatype width.

Stage 1 — correctness-first CUDA kernel

Begin with one CUDA thread, or one logical serial accumulator within a thread, per output element: 

idx = output element
acc = zero

for k in deterministic order:
    x = load_input(...)
    w = load_weight(...)
    p = product(x, w)
    acc = add_acc(acc, p)

acc = add_bias(acc)
output[idx] = activate_and_requantize(acc)

This is simple, deterministic, and exposes substantial parallelism over batch, output channels and spatial outputs.

Stage 2 — tile output work

Let each CUDA block compute a tile of output elements and use shared memory where it provides real reuse of weights or input windows. Preserve the defined reduction order within each output accumulator.

Stage 3 — vectorized memory transactions

Although values initially occupy one byte each, memory can be fetched in wider words such as uint32 and unpacked into multiple codes. Later packed FP4/INT4 modes may fetch even more values per transaction.

Stage 4 — branchless datatype operations

Minimize divergent branches inside the MAC loop. Prefer bit masks, predication, integer arithmetic and compile-time constants for sign/exponent/mantissa extraction and special-case handling.

Stage 5 — compile specialized kernels

Avoid a single runtime kernel containing large datatype switch statements. Use templates or generated specialized kernels so datatype behavior and accumulator behavior are compile-time constants. 

template<
    typename InputFormat,
    typename WeightFormat,
    typename AccFormat,
    MacMode Mode
>
kernel(...)

This naturally supports:

  • FP6 E3M2 versus FP6 E2M3,
  • INT6, Posit6, Log6, etc.,
  • different weight and activation formats,
  • native versus widened accumulators,
  • MAC Models A/B/C.

Once the numerical engine is stable, fuse common chains such as:

Conv + Bias + ReLU/ReLU6 + Requantize

This reduces intermediate global-memory writes without changing numerical semantics.

Stage 8 — optimize only dominant operators

Profile representative networks first. If Conv/DWConv/Linear dominate runtime, prioritize them and keep pooling, residual adds and simple activations as straightforward exact kernels.

Performance target

Set an engineering target for the screening stage:

approximately 1,000 ImageNet images in < 1–2 minutes per ResNet18-sized configuration on a basic Colab NVIDIA GPU

This is a target, not a guaranteed result. If the exact arithmetic backend is slower, the staged candidate funnel and experiment-level parallelization remain the primary controls on total runtime.

GPU scheduling policy

On a weak single Colab GPU, prefer one well-batched experiment at a time. Do not run many independent GPU processes unless profiling shows spare capacity. Across multiple GPUs/machines, distribute whole independent experiment configurations.

Statistical treatment of screening subsets

The 1,000-image and 5k–10k stages are approximations of full-dataset quality. They must be used to estimate uncertainty, not treated as exact rankings.

Use identical evaluation images for every candidate

For a given workload and screening stage, every format/configuration sees exactly the same images in exactly the same predefined subset.

S1000, S10000 are fixed across all compared candidates

This makes candidate comparisons paired and substantially reduces the noise caused by some images being inherently easier than others.

Compare degradation relative to the FP32 reference on the same images

For classification, define per-image correctness difference:

di = I[quantized prediction is correct] − I[FP32 prediction is correct]

Then:

ΔAccuracy = (1/N) Σ di

Store the full paired outcome counts:

  • both FP32 and quantized correct,
  • FP32 correct / quantized wrong,
  • FP32 wrong / quantized correct,
  • both wrong.

Paired bootstrap confidence intervals

Use paired bootstrap resampling over image IDs to estimate uncertainty in ΔTop-1, ΔTop-5 and other aggregate metrics where applicable. A practical default is several thousand bootstrap resamples because this analysis is tiny compared with CNN inference.

example result: ΔTop-1 = −0.8 percentage points, 95% CI = [−1.5, −0.2]

For detector metrics such as COCO mAP, use dataset-level bootstrap/resampling appropriate to the evaluation implementation rather than pretending mAP is a simple Bernoulli accuracy.

Interpretation of the 1k stage

The 1,000-image stage is not a precise ranking stage. A difference of a few tenths of a percentage point is not sufficient evidence to eliminate one candidate in favor of another.

The 1k stage should answer:

  • Is the configuration numerically functional?
  • Is degradation obviously catastrophic?
  • Is the candidate clearly promising?
  • Is the result too uncertain to judge yet?

Calibration-subset robustness

The full search uses the frozen calibration subset for efficiency. For a small finalist set, repeat calibration with several alternative fixed seeds and report whether ranking and degradation remain stable.

Conservative candidate pruning and promotion

Core rule: uncertainty causes promotion to a larger evaluation set, not elimination. The early stages should remove broken configurations, not aggressively narrow the scientific search space.

Stage 0 — numerical and implementation sanity

Reject only objectively invalid/broken runs before dataset screening:

  • oracle/backend mismatch,
  • invalid arithmetic semantics,
  • NaN/invalid-value explosion when not supported by the format,
  • all-zero or constant outputs caused by implementation/configuration failure,
  • near-random prediction caused by obvious catastrophic numerical collapse.

A failed configuration does not automatically eliminate its datatype.

Stage 1 — 1,000-image screening

Run the broad candidate set on the same stratified ≈1,000-image subset. Do not use this stage for fine ranking.

Assign candidates to broad states:

PROMISING    |    UNCERTAIN    |    CATASTROPHIC / BROKEN
  • Promising: automatically promote.
  • Uncertain: automatically promote; more data is required.
  • Catastrophic: diagnose first. Remove the configuration only when failure is genuine rather than caused by an obviously unreasonable accumulator/scale choice.
There is intentionally no hard “top-N survives” rule at 1k. Numeric thresholds, if used for diagnostics, are provisional and must not eliminate close or uncertain candidates.

Family-preservation rule

Before eliminating an entire major datatype family, evaluate at minimum:

  • at least one reasonable scaling configuration,
  • at least one reasonable widened-accumulator configuration,
  • at least two representative CNN workloads,
  • a second reasonable PTQ/calibration variant if the family appears unexpectedly poor under the baseline method.

This prevents conclusions such as “Posit is poor” when only “Posit6 + native accumulator + one scale policy on one network” was actually poor.

Stage 2 — 5k–10k validation

Promote a deliberately broad set:

  • all promising candidates,
  • all statistically uncertain candidates,
  • at least one strong representative of every surviving datatype family,
  • candidates with unusually attractive expected hardware efficiency,
  • candidates close to the current numerical/hardware Pareto envelope.

This is the first stage where meaningful comparative ranking begins, but overlapping confidence intervals still prevent aggressive elimination.

Hardware-aware preservation

Accuracy alone is not sufficient for pruning. A candidate with modestly lower accuracy may still be valuable if it saves substantial area or energy.

Candidate A is only safely dominated when another candidate B is convincingly no worse in quality and no worse in the relevant hardware metrics:

AccuracyB ≥ AccuracyA,   AreaB ≤ AreaA,   EnergyB ≤ EnergyA,   ThroughputB ≥ ThroughputA

Pareto uncertainty buffer

Keep candidates close to the apparent Pareto front rather than preserving only mathematically exact current Pareto points. The buffer accounts for:

  • subset sampling error,
  • calibration variation,
  • later accumulator/scaling optimization,
  • uncertainty in early hardware estimates.

Exact numerical buffer thresholds should be chosen after pilot variance measurements rather than frozen before any data exists.

Cross-workload preservation

Evaluate both average and worst-case degradation across workloads. Keep candidates that are consistently good, exceptionally strong on an important workload, or uniquely hardware-efficient. Do not collapse all models into one mean score too early.

Weight/activation asymmetry preservation

Uniform W=A performance must not be the sole criterion for survival. Every surviving major family should receive at least a small W/A-asymmetry exploration because some formats may be excellent for weights but less suitable for activations.

Stage 3 — full validation

Full ImageNet/COCO validation should still include a relatively broad finalist set—approximately 20–40 configurations if computationally practical. Strong elimination decisions should be made here, not after the 1k stage.

Frequency sweep instead of one arbitrary clock target

A single target clock can distort area comparisons because synthesis may aggressively upsize one design while another meets timing easily. Each implementation should therefore be synthesized across several progressively tighter timing constraints.

implementation → {T1, T2, …, Tn} → area / power / slack / Fmax curve

The exact frequencies should be selected after a pilot on ICS55 rather than guessed in advance. Report both:

  • iso-frequency comparison — all designs at one or more common clocks that they can meet,
  • architecture-optimized comparison — each design at its own best Pareto operating point.

Pipeline depth is part of the search

For architectures where pipelining is meaningful, sweep a small set of pipeline depths, initially around 0–3 internal stages. At these very small operand widths, very deep pipelines are unlikely to be efficient, but the tool should determine the Pareto outcome.

Report:

  • logic area,
  • pipeline-register area,
  • clock-related power for pipelined finalists,
  • latency in cycles,
  • initiation interval (II),
  • throughput = f / II.

Iterative and serial designs

Bit-serial, digit-serial and iterative multipliers must not be penalized or rewarded using frequency alone. For each such design record:

latency, II, operations/s, energy/op, area

A 3-cycle fully pipelined unit with II=1 is fundamentally different from a 3-cycle iterative unit with II=3.

Standard timing harness

Compare combinational arithmetic blocks inside a standardized register-to-register harness:

launch DFF → DUT → capture DFF

Wrapper registers exist only to define realistic launch/load conditions and are excluded from core arithmetic area for a purely combinational DUT. Internal pipeline registers belonging to the architecture are included.

MAC / FMA architecture families

Implement architectures corresponding to the numerical MAC models:

  • separate multiply + add with independent product rounding,
  • narrow product + wider accumulator,
  • fused multiply-add with one final normalization/rounding event,
  • carry-save / redundant accumulation where useful,
  • Kulisch-style or exact fixed-point accumulation followed by final rounding.
Kulisch / exact accumulation is a high-priority candidate. Low-bit floating-point products may map efficiently into a bounded exact/fixed aligned accumulator, potentially improving both quality and hardware efficiency compared with repeatedly normalized FP addition.

Posit architecture space

Evaluate:

  • ordinary Posit decode → significand multiply/add → normalize → encode,
  • wider Posit accumulation,
  • Posit + quire dot-product architectures.

MX / BFP architecture space

Search choices for:

  • block exponent / scale detection,
  • shared-scale storage and distribution,
  • element arithmetic using INT, minifloat or small mantissa datapaths,
  • scale-early versus scale-late execution,
  • integer/fixed partial sums before applying block scales,
  • wide block accumulation and final requantization.

Logarithmic architecture space

Multiplication is cheap in the log domain:

log2(xy) = log2(x) + log2(y)

For addition/accumulation compare:

  • full LNS addition with correction LUT,
  • segmented LUT correction,
  • piecewise-linear correction,
  • shift-add approximation,
  • log-domain multiplication + linear accumulator.

Codebook / non-uniform architecture space

Compare:

  • decode codebook value → conventional arithmetic,
  • direct 2D product LUT indexed by the two low-bit codes,
  • segmented/shared decode structures,
  • small LUT + wider accumulator combinations.

Binary and ternary extreme-efficiency points

  • binary XNOR + popcount / sign-select accumulation,
  • ternary −x / 0 / +x select-and-accumulate with zero gating,
  • 2-bit multi-level shift/add or LUT implementations.

Approximate arithmetic policy

Approximate multipliers/adders belong to a separate optional branch. The primary datatype study uses exact arithmetic so datatype quantization error is not confounded with circuit approximation error. Approximate arithmetic can be explored later as an additional co-design dimension.

Pdynamic, Pleakage, Pclock where available, Ptotal

Then derive:

Energy/op = Ptotal / Throughput
EDP = Energy/op × operation latency

Area/energy/throughput Pareto plots are the primary presentation. EDP can be reported as an auxiliary scalar metric.

Clock power must count

Pipeline-register and clock-tree power must be included for pipelined finalists. A deeply pipelined design must not appear artificially efficient by counting only its combinational datapath.

Glitch-power policy

Zero-delay simulation can underestimate combinational dynamic power because hazards/glitches are absent. For the final 2–4 candidates, perform delay-aware post-route switching analysis if the PDK and open flow support it reliably.

If ICS55 preview data does not support a reliable extracted-delay/glitch methodology, state that limitation explicitly and report activity-based non-glitch dynamic power for ICS55. Optionally validate the delay-aware methodology using a more mature open PDK rather than inventing unsupported precision.

Power estimation does not require the full ImageNet validation set. Use a fixed representative image subset and check convergence as trace length grows, for example:

32 → 64 → 128 → 256 images

Do not report only storage capacity. For each datatype / memory organization, measure or estimate:

  • usable capacity,
  • physical area,
  • read energy,
  • write energy,
  • read/write latency,
  • delivered bandwidth,
  • effective bits/value after padding and metadata.

Memory energy per inference

Ememory,inf = NreadEread + NwriteEwrite

Count accesses separately for weights, activations, accumulators, scale metadata and other local structures where relevant.

Ideal versus physical scaling result

One explicit analysis should compare the theoretical bit saving against the physically realizable area/energy saving. The difference itself may be an important result: a 5-bit format can have a 37.5% ideal storage advantage while a real macro organization preserves substantially less.

Memory sensitivity cases

For finalists, compare at least:

  • same number of stored values,
  • same physical memory area,
  • same memory bandwidth budget,
  • same model working set / cache-locality requirement.
Primary principle: arithmetic savings and memory savings are evaluated separately first, then combined at the tile/chip level. A datatype is not credited with ideal SRAM savings if the chosen physical memory organization cannot realize them.

3. Scale application by datatype family

INT with arbitrary real-valued scale

qout = Round(qacc × (sxsw/sout))

The practical hardware path may use an integer multiplier, fixed-point multiplier, shift, rounding and clamp. Compare optimized requantization hardware rather than charging a generic full multiplier automatically.

INT with power-of-two scale

Scale application largely reduces to shifts plus rounding/saturation. This is a key hardware-oriented ablation.

FP/minifloat with power-of-two scale

Scaling can often be implemented as exponent adjustment rather than a general multiply.

FP/minifloat with arbitrary scale

Explore optimized choices such as folding weight scales offline, combining output scaling with requantization, reusing an existing multiplier, or encoding scale partly through exponent/bias manipulation where valid.

MX / BFP

Compare two main architecture strategies:

  • scale early — apply element/block scales before or during each product,
  • scale late — accumulate raw low-precision block products, then apply s_x × s_w to the block partial sum.

Scale-late execution may amortize scaling hardware over many MACs and should be an explicit architecture-search dimension.

Posit

General external scale may require an additional multiply, while power-of-two scaling may be implemented through magnitude/regime/exponent manipulation. Synthesize both reasonable implementations rather than assigning a theoretical cost.

Logarithmic formats

log2(sx) = log2(x) + log2(s)

External scaling can therefore become a small addition in the log domain, which may be a hardware advantage.

Report scale reads, storage and movement separately. For per-tensor scaling this can be nearly negligible; for block-16/32 scaling it may become meaningful.

Arithmetic-unit PPA is not the final selection criterion. The final question is: under the same silicon/power constraints and measured model quality, which numerical architecture produces the best complete accelerator?

The generic model contains only publishable components such as a parameterized PE/MAC, accumulator, scaling/conversion logic, local memory, control overhead and bandwidth assumptions. Complete tile-cost equation

For datatype/configuration F:

Atile(F) = Acompute + Aaccumulator + Ascale/conversion + Alocal-memory + Acontrol + Alocal-interconnect

Shared chip resources are accounted for separately:

Achip = Ashared + NFAtile(F)

For a fixed area budget:

NF = floor((Abudget − Ashared) / Atile(F))

Peak and effective throughput

If a tile sustains r useful operations/cycle:

Throughputpeak = NF × rF × fF

Actual workload performance must include utilization:

Throughputeffective = Throughputpeak × UF

Prefer direct workload metrics such as images/s from the mapped network rather than relying only on nominal TOPS.

Datatype-aware bandwidth roof

Effective throughput is bounded by multiple resources:

T = min( Tcompute, Tlocal-memory, Tinterconnect, Texternal-memory )

Lower precision can simultaneously increase compute density and reduce memory/interconnect traffic, so both effects must be represented. A datatype is not credited with additional compute units if another resource prevents those units from being utilized.

End-to-end energy per inference

Einf = Ecompute + Elocal-memory + Escaling/conversion + Einterconnect + Eoff-chip + Econtrol + Eleakage

Leakage contribution is time dependent:

Eleakage = Pleakage × Tinference

This prevents a tiny but slow iterative implementation from looking artificially attractive when only dynamic energy/op is considered.

Pareto-based final objective and decision framework

The research should not force one universal “best datatype” through an arbitrary scalar score. The primary result is a set of accuracy–energy–area–throughput Pareto frontiers.

Pareto dominance definition

Accuracy_B ≥ Accuracy_A
Energy_B ≤ Energy_A
Area_B ≤ Area_A
Throughput_B ≥ Throughput_A

Configuration A is dominated only when another configuration is no worse in every relevant dimension and strictly better in at least one. If FP6 is more accurate while INT5 is substantially smaller and more energy efficient, both remain valid Pareto points.

Quality-budget frontier

E*(δ) = min_{c : ΔQuality(c) ≤ δ} E(c)

Define analogous frontiers for area and throughput and evaluate multiple quality-loss budgets, for example 0.25, 0.5, 1, 2, 3 and 5 percentage points. This avoids making one arbitrary loss threshold the entire objective.

Knee-point analysis

Identify points where a small additional quality gain begins to require disproportionately more energy or area. Knee points are useful engineering candidates but are not presented as mathematically unique winners.

Per-workload Pareto fronts first

L_max(F) = max_m ΔQuality(F,m)

Statistical uncertainty from paired confidence intervals carries into dominance decisions. Classify configurations as confidently Pareto-optimal, potentially Pareto-optimal / uncertainty-overlapping, or confidently dominated.

12. Architecture-independent exact inference engine

To keep the numerical-format paper independent of unpublished MANT details, quality evaluation should use a generic exact-arithmetic backend rather than the MANT simulator. Each datatype should implement the same interface: 

NumberFormat
    encode(fp32)       → low-precision code
    decode(code)       → high-precision reference value
    add(a, b)          → rounded datatype result
    mul(a, b)          → rounded datatype result
    requantize(x)      → target storage format
    convert(src, dst)  → explicit format conversion

Truth-table oracle

Since every candidate datatype is 8 bits or smaller, each binary operator can be exhaustively enumerated. For an n-bit format, there are only 2^n × 2^n input pairs.

A high-precision implementation generates exact ADD/MUL truth tables. Every optimized C++ or CUDA implementation is then exhaustively checked against those tables before it is used for CNN inference.

Validation rule: the fast backend is accepted only if every possible operand pair matches the reference arithmetic bit-for-bit.

LUTs versus direct arithmetic

Lookup tables are ideal as a correctness oracle. For actual CNN execution, direct CUDA integer/bitwise arithmetic with explicit rounding may be faster, especially for 7–8-bit formats where dependent table lookups can become memory-bound. Benchmark both approaches for 4–6-bit candidates.

13. Compute strategy and parallelization

The study should exploit two forms of parallelism: parallelism inside one inference run and parallelism across independent experiment runs.

13.1 GPU: parallelize inside one experiment

On a basic NVIDIA Colab GPU, one experiment should normally occupy the GPU at a time. Parallelize over:

  • batch dimension,
  • output channels,
  • output pixels,
  • independent convolution/GEMM tiles.

The reduction inside one low-precision dot product remains ordered, but CNN layers provide a very large number of independent outputs. Custom CUDA kernels should exploit this outer parallelism.

Do not run many independent experiment processes on one weak Colab GPU unless profiling proves it helps. They will usually compete for memory and execution resources. Prefer one well-batched job per GPU.

13.2 CPU: parallelize across experiments

On an M1 or Core i9, different model/format/accumulator configurations are independent jobs. A worker pool can execute multiple experiments simultaneously. 

worker 0 → ResNet18 / FP6-E3M2 / native accumulator
worker 1 → ResNet18 / INT6      / 12-bit accumulator
worker 2 → MobileNetV2 / FP6-E2M3 / native accumulator
worker 3 → MobileNetV3 / Posit6 / 12-bit accumulator

Benchmark both “few jobs with many threads each” and “many jobs with fewer threads each.” On a high-core-count i9, experiment-level parallelism is likely useful until memory bandwidth becomes the bottleneck. The M1 is well suited for development, exact validation and smaller runs; the GPU/i9 should carry the bulk of large sweeps.

13.3 Multi-machine scheduling

Store each experiment as an independent configuration/job so runs can be distributed across local machines, lab servers, multiple GPUs or future cloud resources. No experiment should depend on another once calibration metadata and quantized weights are cached.

The strongest version of the project is not “find the best datatype below 8 bits.” It is:

Find the best numerical architecture for sub-8-bit edge CNN inference under real silicon constraints.

Jointly select:

  • weight format,
  • activation format,
  • accumulator format,
  • scaling granularity,
  • signedness,
  • tile implementation.

For MANT, the most promising early comparisons are: FP6 vs INT6 vs MXFP6, same-format vs wider accumulation, signed vs unsigned activations, and uniform vs heterogeneous tile specialization. All accuracy experiments in the current plan use PTQ only.

If the exploration is executed in this order, the research and chip work reinforce each other: the experiments determine what chip should be built, and the chip gives the paper a credible end-to-end hardware platform.
